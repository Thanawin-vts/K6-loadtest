==================================================
BIDDING KPI ENHANCEMENT
IMPLEMENTATION ANALYSIS & PLAN
==================================================

## 1. OBJECTIVE

Add 2 new bidding latency KPIs to the existing k6 performance
test and report.

The existing KPIs must remain unchanged.

The implementation scope covers the complete flow:

k6 test
    ↓
WebSocket bidding flow
    ↓
KPI calculation
    ↓
k6 metrics
    ↓
report data
    ↓
report generation
    ↓
final report


## 2. BUSINESS RULE

1. Existing KPIs
   - Keep all existing KPIs unchanged.
   - Do not modify their existing calculation logic.
   - Do not change their existing names or behavior unless required.

2. Bidding KPI
   - Measure the duration of every bidding transaction.
   - There are 2 response cases.

   2.1 Bidding Success
       Start:
         When bidding is sent through WebSocket.

       End:
         When the corresponding bidInfo WebSocket message is received.

       KPI:
         bidding_success_duration

   2.2 Bidding Failure
       Start:
         When bidding is sent through WebSocket.

       End:
         When the corresponding notification WebSocket message
         with level = error is received.

       KPI:
         bidding_failure_duration


## 3. REQUIRED WORKFLOW

The implementation must cover:

1. k6 test
2. WebSocket message handling
3. Bidding request tracking
4. Response correlation
5. KPI calculation
6. k6 metric registration/recording
7. Metric export
8. Report data processing
9. Report generation
10. Final KPI presentation


## 4. IMPORTANT CONSTRAINT

DO NOT IMPLEMENT CODE IN THE FIRST PHASE.

First analyze the existing codebase and produce an
implementation plan.

The analysis must be based on the existing implementation.
Do not assume or invent behavior that is not present in the code.

## 6. CORRELATION ANALYSIS

Determine how the existing implementation identifies
which response belongs to which bidding request.

Analyze:

bidding request → bidInfo

and:

bidding request → error notification

The implementation must not incorrectly match responses
when multiple bidding requests are active.

If the existing implementation does not contain sufficient
correlation information, document the gap before proposing
a solution.


## 7. TIMING DEFINITION

Success:

bidding_success_duration =
    bidInfo_received_timestamp
    -
    bidding_sent_timestamp


Failure:

bidding_failure_duration =
    error_notification_received_timestamp
    -
    bidding_sent_timestamp


Use the existing timing mechanism where appropriate.

Do not introduce a different timing mechanism without
explaining why.


## 8. NEW KPI

### 8.1 bidding_success_duration

Purpose:
Measure the duration from sending bidding to receiving
the corresponding bidInfo message.

Expected metric type:
Trend

Required statistics:

- avg
- min
- med
- max
- p90
- p95


### 8.2 bidding_failure_duration

Purpose:
Measure the duration from sending bidding to receiving
the corresponding notification with level=error.

Expected metric type:
Trend

Required statistics:

- avg
- min
- med
- max
- p90
- p95
